Lab 6: extraer estadísticas a microservicios

ENUNCIADO PROPUESTO

1. Objetivo y contexto

A partir de la aplicación del Lab 6, extraer el cálculo de estadísticas hacia un backend de microservicios, conservando el acceso con Firebase y el registro de sesiones en Firestore.

Actualmente Android conoce las sesiones y calcula totales por mes y actividad. En esta variante, Android debe solicitar esos totales por HTTP y utilizarlos para dibujar sus gráficos.

Duración sugerida: 60 minutos con proyectos base preparados. La primera descarga de dependencias puede consumir tiempo adicional. Este enunciado es una práctica creada para estudiar; no reemplaza instrucciones del docente.

ENUNCIADO PROPUESTO

2. Arquitectura solicitada

Android → Reportes :8020 → Estadísticas :8010
Reportes utiliza Feign para llamar a Estadísticas por su nombre lógico.
Reportes ↔ Eureka :8761 ↔ Estadísticas
ComponenteResponsabilidad
AndroidAutenticar, leer sus sesiones de Firestore, enviar datos y filtro por HTTP y dibujar los resultados.
servicio-reportesRecibir la solicitud externa, consultar Estadísticas con Feign y preparar un mensaje del reporte.
servicio-estadisticasValidar los datos, aplicar el filtro por curso y calcular los totales.
Eureka ServerRegistrar las instancias y permitir descubrir Estadísticas por nombre.

El tráfico de negocio viaja directamente entre Reportes y Estadísticas. Eureka no suma horas ni retransmite el cuerpo del reporte.

ENUNCIADO PROPUESTO

3. Requisitos funcionales

  1. Conservar inicio de sesión, registro, recuperación, cierre de sesión y CRUD de sesiones del Lab 6.
  2. Crear un Eureka Server en el puerto 8761.
  3. Registrar los servicios servicio-estadisticas y servicio-reportes.
  4. Estadísticas debe recibir una lista de sesiones y un curso opcional. Curso nulo o vacío significa todos los cursos.
  5. Calcular cantidad de sesiones, total de horas, horas por mes/año y horas por tipo de actividad. Admitir horas decimales.
  6. Reportes debe llamar a Estadísticas mediante @FeignClient(name = "servicio-estadisticas"), sin fijar su URL en Java.
  7. Reportes debe añadir un mensaje legible con curso, cantidad y total de horas.
  8. Android debe enviar todas sus sesiones y el curso seleccionado. Los cálculos se ejecutan en Estadísticas.
  9. El filtro debe afectar a ambos gráficos. Los cambios de Firestore deben permitir actualizar el reporte.
  10. Mostrar un estado de carga y un error comprensible cuando falle la consulta. Evitar bloquear el hilo de interfaz.

No se solicita implementar un gateway, Docker, una nueva base de datos, fallback automático o credenciales de administrador de Firebase. El backend del ejercicio procesa las sesiones recibidas y no las persiste.

ENUNCIADO PROPUESTO

4. Contrato HTTP

ServicioMétodo y ruta
ReportesPOST http://localhost:8020/reportes
EstadísticasPOST http://localhost:8010/estadisticas

Ambas peticiones utilizan Content-Type: application/json y el mismo cuerpo. Cada fecha se envía como texto yyyy-MM-dd.

JSON · solicitud de ejemplo
{
  "curso": "IoT",
  "sesiones": [
    {
      "curso": "IoT",
      "fecha": "2026-11-17",
      "horasDedicadas": 1.5,
      "tipoActividad": "Teoría"
    },
    {
      "curso": "IoT",
      "fecha": "2026-11-18",
      "horasDedicadas": 2,
      "tipoActividad": "Laboratorio"
    },
    {
      "curso": "Redes",
      "fecha": "2026-10-12",
      "horasDedicadas": 3,
      "tipoActividad": "Práctica"
    }
  ]
}

La respuesta de Reportes debe incluir:

JSON · respuesta de ejemplo
{
  "cantidad": 2,
  "totalHoras": 3.5,
  "horasPorMes": {
    "2026-11": 3.5
  },
  "horasPorActividad": {
    "Teoría": 1.5,
    "Práctica": 0.0,
    "Laboratorio": 2.0
  },
  "mensaje": "IoT: 2 sesiones · 3,50 horas"
}

El separador decimal del mensaje es presentación; los números JSON usan punto. Estadísticas devuelve los mismos valores numéricos; Reportes prepara el mensaje.

ENUNCIADO PROPUESTO

5. Validaciones y estados HTTP

  • Curso de cada sesión: obligatorio, no vacío y de hasta 100 caracteres.
  • Fecha: obligatoria, válida y en formato ISO yyyy-MM-dd.
  • Horas: número finito mayor que 0 y como máximo 24.
  • Actividad: Teoría, Práctica o Laboratorio.
  • Una lista vacía es válida y devuelve ceros. Una lista ausente no es válida.
  • Meses iguales de años distintos deben mantenerse separados.
EstadoCuándo
200Reporte calculado, incluso si no hay sesiones para el filtro.
400Datos inválidos o cuerpo mal formado.
503Reportes no puede consultar Estadísticas.

ENUNCIADO PROPUESTO

6. Pruebas de aceptación

  1. Mostrar ambos servicios registrados en el dashboard de Eureka.
  2. Enviar la solicitud de ejemplo: IoT debe devolver 2 sesiones y 3.5 horas.
  3. Enviar el mismo cuerpo con curso nulo: debe devolver 3 sesiones y 6.5 horas.
  4. Verificar noviembre con 3.5 horas y octubre con 3 horas al consultar todos los cursos.
  5. Enviar lista vacía: total 0, cantidad 0, meses vacíos y las tres actividades en 0.
  6. Enviar horas negativas y una fecha imposible: recibir 400.
  7. Probar desde Android el filtro y los gráficos con las sesiones reales del usuario.
  8. Detener Estadísticas y consultar Reportes: recibir un error 503, sin resultados inventados.
